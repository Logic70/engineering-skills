# Engineering Skills

将可用功能变更从设计推进到分支实现、PR 审查、授权合入和独立验收，保留文档与 Git 记录的轻量 skill 组合包。
首版面向 Codex，使用普通 `SKILL.md`，不引入工作流引擎、模型服务或外部代理依赖。
从 `engineering-workflow` 开始；小修复保持精简，跨模块变更明确设计契约。
合入、独立验收和发布是不同结果。

[English](README.md) | [设计](docs/design.md) | [示例](examples/change-record.md) | [验收记录](docs/verification.md)

## 包含什么

| Skill | 职责 |
| --- | --- |
| `engineering-workflow` | 总入口：选择功能切片，协调角色、依赖和交接 |
| `highlevel-design` | HLD：架构边界、用户/逻辑/部署视图及验证约束 |
| `lowlevel-design` | LLD：文件、接口、数据、异常与测试映射 |
| `design-plan-closure-review` | 对设计和计划反复审查、修订，直到问题闭环 |
| `engineering-implement` | 开发分支实现、单元测试和适用自测、产品缺陷修复 |
| `engineering-test` | 提前从需求和设计准备用例；独立验收实际 main |
| `engineering-review` | 审查 PR 的代码缺陷、回归风险和测试缺口 |
| `engineering-deliver` | 记录证据、提交相关 Git 变更，报告交付与验收状态 |

## 安装

需要 Git 和 Python 3.10+；skill 内容本身不依赖 Python。

```sh
git clone https://github.com/Logic70/engineering-skills.git
cd engineering-skills
python scripts/install.py --dest /path/to/project/.agents/skills --dry-run
python scripts/install.py --dest /path/to/project/.agents/skills
```

Windows 下将目标换为带引号的实际路径。也可显式指定 Codex 用户级
`~/.codex/skills` 目录，Windows 建议使用完整路径。必要时重新启动代理会话以发现新 skill。
安装只复制八个 skill 目录，不覆盖已有文件；任一同名目录或文件存在就会提前停止。
已有同名 HLD/LLD 等 skill 时，先人工比较，或安装到干净的项目目录。
项目级与用户级 skill 可能互相遮蔽，应确认代理实际加载的版本。
复制中途遇到磁盘或权限错误时会报告失败，但可能留下部分目录；重试前需人工检查，
只清理确认属于该次失败安装的文件，安装器不会自动删除用户文件。
其他代理能否自动发现取决于其自身机制，本包不声称已经完成跨代理兼容性验证。

## 使用

```text
使用 $engineering-workflow，在 <仓库路径> 完成 <变更目标>。
遵守项目指令，保留无关的已有修改。
```

也可单独调用 `$engineering-test` 或 `$highlevel-design` 等。它们是代理指令，不是终端命令。
只要求设计或审查时，不自动修改业务代码、提交或发布。

选择一个小而可用的业务流程，明确真实保存结果或阶段交接，以及可观察的成功证据。
复用已完成的基础，只更新受影响的 HLD/LLD；小修复可用简短设计说明和计划代替完整设计文档。
设计描述系统如何工作，计划描述实施顺序，两者分开。
优先实现功能；非阻塞的性能优化、极端场景加固和兼容性工作进入已有待办，
但不能因此删除约定的最终需求或验收范围。阻塞正确性、授权、证据真实性、数据完整性，
以及必要的取消和清理仍须保证。

职责分开，不让协调者重复完成所有角色的工作：

| 角色 | 负责 |
| --- | --- |
| 设计 | 受影响的 HLD/LLD、接口、数据交接，以及设计遗漏与冲突 |
| 开发 | 分支实现、单元测试、适用自测、PR 和产品缺陷修复 |
| 测试 | 提前从需求和设计准备用例/数据/自动化；独立 main 验收和复验 |
| 协调 | 优先级、依赖、文件归属、权限边界、证据覆盖和清晰报告 |

独立验收负责人不能是该功能的产品代码作者；编写验收用例或执行器本身不影响测试角色的独立性。
按功能分配角色，不要求每个角色全程占用代理；仅并行前置条件已满足、文件归属明确的工作。

正常交付主线：

```text
功能范围 → 受影响的设计/计划闭环
         → 开发分支实现 + 单元测试/自测 → 提交/PR
         → 代码审查 + 合入检查 + 授权 → 合入 main
         → 独立验收已标识的实际 main 提交
测试在开发期间提前准备基于需求/设计的用例。
```

开发自测后创建 PR，再完成代码审查和合入；不能要求创建 PR 前先完成该 PR 的审查。
这里的 main 指项目权威集成分支，不另造集成分支。测试只对固定的实际 main SHA 执行验收，
使用干净隔离检出或准确源码导出，不验收功能分支、PR 合并预览或叠加未合入产品修改的版本。
记录产品 SHA 和用例/执行器版本；单元测试或 mock 结果不能代替所要求的真实业务流程与阶段交接验收。

明确实现错误直接带复现和证据退回开发；需求/契约歧义由设计澄清，新的业务取舍交回用户。
修复走开发/修复分支 → 自测 → PR/审查 → 授权合入 main → 受影响行为的 main 复验。
对齐预期不能把已证明的失败改成通过。待执行的合入后验收不能用来绕过已失败的合入检查；
合入不等于验收通过，也不等于发布。

优先复用项目已有文档、issue、PR 和测试工具；没有持久记录位置时才在仓库保存简短变更记录，
不新增跟踪系统。[示例](examples/change-record.md) 将开发证据、交付和 main 验收分开，
只是模板，不是实际应用执行证据。提交号在提交后报告或更新已有外部记录，不反复提交以写入自身提交号。

## 安全与边界

- 项目指令、用户意图和工具权限优先。保留用户明确暂停；独立的策略或文档请求不恢复暂停的产品工作或任务。
  本包不授予合入、部署、安装、账户/服务、生产环境或模型/数据外发权限。
- 正常实现任务在没有禁止指令时包含相关本地 Git 提交，但 push、公开发布、外部代理委派、架构变更和破坏性 Git 操作不能隐式执行。
- 分别报告通过、失败和未验证范围。只有相关源码、锁文件、工具链和配置未变且可识别时才复用支撑性检查，
  不能把分支结果改称 main 验收。未执行检查仍未执行，语法检查不等于行为验收。
- 纯文档或协作策略维护可用静态差异、链接和一致性检查，将产品验收标记为不适用。
  运行时提示词、产品使用的 skill、目录输入和测试夹具不能仅因 Markdown 扩展名而豁免。
  共享行为或最终集成应扩大回归，不对每次文档编辑都跑无关套件。
- 保留已有修改，不提交无关工作、凭据、机器私有配置或原始执行日志。
- 本包不含调度器、外部编程代理、工作流引擎或 WorkflowProgram 插件代码。
